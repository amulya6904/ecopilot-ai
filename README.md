# EcoPilot AI

Autonomous Smart Building Energy and Comfort Optimization for the Honeywell
recruitment hackathon.

## Official target

EnergyPlus is the required primary high-fidelity simulation engine for the final
baseline and AI-driven closed-loop evaluation. The target system will stream
EnergyPlus telemetry through a backend abstraction to bounded MCP tools and an
open-source LLM such as Qwen, Mistral, or Llama. Structured control proposals must
pass a deterministic safety validator before setpoints or supervisory overrides
are injected into the next EnergyPlus interval.

This repository does **not** yet execute EnergyPlus, connect an LLM, expose MCP
tools, or run a closed loop. Phase 4 will begin that work.

## Current implemented phases

- Phase 1: configuration and architecture foundation — updated and complete
- Phase 2: Lightweight Development Simulator — complete
- Phase 3: lightweight fixed-schedule development baseline — complete
- Phase 4 onward — not started

The existing three-zone custom simulator is preserved as a lightweight development
digital twin test harness and fallback backend. It validates control interfaces,
telemetry pipelines, metrics, reproducibility, and UI behavior before EnergyPlus is
connected. It is not the official final simulation engine.

The Phase 3 fixed schedule is likewise a development benchmark. It provides energy,
cost, carbon, temperature-comfort, CO2, power, and zone summaries without claiming
official savings.

## Important result classification

Development outputs:

- are generated by the Lightweight Development Simulator;
- validate controllers, metrics, data flow, exports, and dashboards;
- are stored under `results/development/` with compatibility copies under `data/`;
- are not final official savings evidence.

Official outputs:

- must be generated by EnergyPlus;
- must compare baseline and agent scenarios using identical IDF and EPW conditions;
- must include percentage kWh reduction and evidence that comfort is preserved;
- will be stored under `results/official/`.

The official directory is intentionally empty except for `.gitkeep`.

## Implemented development architecture

`BuildingSimulator` runs 08:00–19:55 in 144 five-minute intervals and emits 432
records across Open Office, Conference Room, and Computer Lab. It models weather,
occupancy, indoor temperature, humidity, CO2, HVAC power, interval energy, price,
carbon intensity, and temperature-based comfort. Seeded independent random streams
preserve reproducibility; heat-wave mode adds 5°C without changing tariff or carbon
tiers.

`LightweightSimulatorBackend` composes this simulator without changing its equations.
It maps existing `ZoneState` and `HVACAction` records to shared schemas. PMV remains
`None` because the lightweight model does not calculate it.

`EnergyPlusBackend` is an unavailable structural placeholder. It raises
`NotImplementedError` for runtime operations and never silently falls back.

## Phase 3 development baseline

| Schedule | Setpoint | Fan | Ventilation |
|---|---:|---:|---|
| Occupied, 09:00–18:00 | 22°C | 80% | Medium |
| Unoccupied | 27°C | 20% | Low |

The controller selects actions using timestamp, zone ID, and configured operating
hours. It deliberately ignores actual occupancy and sensor conditions. It does not
use prediction, an LLM, or optimization.

## Repository structure

- `backends/`: application-facing protocol, lightweight adapter, EnergyPlus placeholder
- `schemas/`: shared building state, control action, and runtime-error records
- `config/`: validated simulation, EnergyPlus, agent, PMV, and peak-demand settings
- `simulator/`: preserved Phase 2 lightweight development simulator
- `controllers/`: implemented fixed baseline and future controller boundaries
- `metrics/`: Phase 3 development-benchmark calculations and classification
- `scripts/`: Phase 2 and Phase 3 command-line validation/export
- `energyplus/`: future model, weather, output, log, and modified-model namespaces
- `energyplus_adapter/`: preserved legacy boundary; `backends/energyplus.py` is the
  future primary application-facing adapter
- `results/development/`: generated lightweight outputs
- `results/official/`: future EnergyPlus-only outputs
- `docs/`: target architecture, requirements mapping, and phase status
- `mcp_service/`, `llm/`: future boundaries only
- `tests/`: regression, interface, schema, documentation, and import-safety tests

## Setup on Windows PowerShell

Python 3.11 or newer is required.

```powershell
python -m venv venv
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

EnergyPlus, Ollama, and MCP dependencies are intentionally not required for current
Phase 1–3 use.

## Run current features

```powershell
python -m pytest -q
python -m scripts.run_phase2_demo
python -m scripts.run_phase3_baseline
streamlit run app.py
```

The CLIs write preferred development paths:

- `results/development/phase2_simulation.csv`
- `results/development/phase3_baseline.csv`
- `results/development/phase3_baseline_summary.csv`

Compatibility copies continue to be written under `data/`.

## Current limitations and next phase

The lightweight model is not building-calibrated and omits detailed thermal mass,
airflow, solar gain, latent loads, equipment cycling, and PMV. Its derived facility
demand is development telemetry, not an official EnergyPlus demand result.

No final baseline-versus-agent savings, PMV compliance, EnergyPlus runtime errors,
LLM decisions, MCP calls, actuator injection, or closed-loop execution is currently
available.

**Next phase: Phase 4 — EnergyPlus Integration.**
